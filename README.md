### 洞察集群解冻：从"电商数据诊断"到"通用数据中台"（2026-12）

阶段 0 曾冻结该项目的"通用数据分析定位"（冻结清单 4.1），理由是"会稀释电商垂类目标"。
该判断**成立**——grep 已证明全项目无电商语义，七节点工作流与业务域无关。
但它是**注意力分配决策，不是代码问题**，本次是上层决策改变：通用性不再是需要收敛的偏差，
而被选定为核心资产。按本仓库维护规则「冻结项恢复时必须先更新文档再改代码」，本次只改文档。

- **解冻的是定位，不是代码能力**：被冻结的从来是一项"不要往通用方向投入"的约束；
  解除它不需要改任何一行代码。4.2 的工程资产原本就要继续投入，本次不变。
- **与 data-hub 的关系变更**：`data_hub` 连接器保留（`backend_py/connectors.py`），
  但降级为**普通数据源类型之一**，与 PostgreSQL / HTTP JSON / 网页抓取并列。
  阶段 1 补的连接器与 14 项验证断言继续有效，未回滚。
- **已具备中台四层能力**：数据接入（7 格式 + OCR + 连接器）、数据开发/加工（LangGraph 七节点
  + Redis 可靠队列）、分析与可视化（指标/ECharts/报告导出）、资产与治理
  （结构化表/RBAC/审计/脱敏水印/local+S3）。缺口清单见该项目 README「距生产级数据中台的缺口」。

### 已验证的事实（不是推断）

- **data-hub 已经存在且已在生产链路中**：`内容生成/apps/data-hub/app.py` 是一个零依赖（标准库 `http.server` + `sqlite3`）的商品知识中心，`hub_products` 表以 `(tenant_slug, external_id)` 为唯一键，提供 `/hub/ingest`、`/hub/products`、`/hub/products/{slug}/{eid}/ack`、`/hub/search` 等接口。**不是新东西，是已跑通的中间层。**
- **内容平台 → data-hub → 电商 已双向打通**：内容侧 `apps/api-server/src/services/data-hub-sync-service.js` 在任务完成回调时自动 ingest；电商侧 `flask_shop/scripts/jobs/sync_from_hub.py` + `flask_shop/scripts/verify/verify_hub_integration.py`（20 项断言）已验收。
- **跨境电商项目已经是纯电商**：`backend/app/services/ecomops_catalog.py` 的 `AGENTS` 列表 12 个 Agent 全部是电商角色（选品、Listing、营销、履约、合规、数据分析…），`ecomops_specialists.py` 的工具输出含 landed cost、毛利率、退款率、转化率、ROAS 等真实电商指标。
- **洞察集群的业务语义完全来自上传数据**：`backend_py/workflow_service.py` 的 `WORKFLOW_NODE_IDS = ["source","clean","metric","chart","analysis","report","audit"]`，节点文案是"数据接入 Agent""指标计算 Agent"这类通用标签，无任何电商语义。
- **内容平台默认打开的是非电商工作区**：`apps/studio-web/src/App.jsx` 中 `useState("ip")`，`IPWorkspace.jsx`（384 行）承载"数字 IP 创作"（世界观设定 / 章节批量创作 / 四节点调研-撰写-润色-审核）。电商的批量 Listing 生成反而是第二个 tab。
- **客服项目有已实现但被隐藏的电商周边能力**：`flask_shop/flask_shop/automation/views.py` 注册了 `ads`（广告 ROI 止损巡检）与 `competitor`（竞品价格排名监控）两条自动化规则，`t_ad_records` / `t_competitor_monitors` 表与路由均为可用状态；README 与 TODO 已明确声明它们暂不进普通商家操作路径。

### 阶段 1：商品主数据契约化（1～2 周）— **已完成（2026-12）**

让"商品"在四个项目里有唯一权威源和一致的字段口径。已有 data-hub 作为事实来源，本阶段做三件事：

1. **字段映射表**：把 4 个项目各自的商品模型对齐到 data-hub 的 `hub_products` schema（见 [商品主数据契约.md](商品主数据契约.md)）。
2. **补两处缺口**：跨境电商项目的 `ProductModel` 缺内容知识字段（卖点/描述/FAQ/图片），洞察集群缺商品上下文入口。两者都通过 REST 消费 data-hub，不新建本地权威表。
3. **不回写**：data-hub 是唯一写入方，其余项目只读 + ack 回执，沿用现有 `published_product_id` 模式。

**实测结果**：

| 项目 | 验证 | 结果 |
| --- | --- | --- |
| 跨境 | ruff + pytest + 新 verify 脚本 | All checks passed / 187 passed / **11/11** |
| 洞察 | pytest + 新 verify 脚本 | 129 passed / **14/14** |
| 客服（data-hub 回归） | `verify_hub_integration.py` | **18/18 PASS**（需先启动 data-hub 并设 `PYTHONIOENCODING=utf-8`） |
| 内容生成 | 无代码改动 | 工作区干净 |

三个缺口落地方式：跨境 `external_id` 加列 + 迁移 `20261015_0018` + 幂等优先级
（`external_id` > `platform_item_id`，命中后补写身份）；跨境只读 client
`backend/app/services/hub_client.py`；洞察 `data_hub` 只读连接器
（`backend_py/connectors.py`）。新验证脚本都不需要真实 data-hub。

**阶段 1 自查出的两个自身 bug（已修）**：洞察连接器 `int(config.get("limit") or 200)`
把显式填 `0` 当成未配置而跳过校验；两个自测桩的问题（`read()` 未分块触发 5MB 上限、
urllib header 键规范化导致 tenant 头误判）。详见 [商品主数据契约.md](商品主数据契约.md) 第五节。

### 其余项目垂直化：内容平台七轮改动

七轮改动，两条主线：**schema 早建好但代码没接上**，以及**权限管得住"能不能写"、管不住"能看谁的"**。

| 轮次 | 发现 | 交付 | 实测 |
| --- | --- | --- | --- |
| 1 身份 | 有 `users`/`projects`/`project_members` 表，但仓储写死 `user_demo` | 身份中间件（off/local/strict）、HMAC 自签 token、用户仓储、注册/登录/me、项目按 owner 隔离 | 28 项新测试；api-server 49 passed |
| 2 权限 | `project_members.role_code` 有字段也写了 `'owner'`，但没有任何一处读它判定 | 项目级权限矩阵（owner/editor/viewer）、成员增删改查、两条 owner 保护 | 24 项新测试；api-server **73 passed** |
| 3 前端 | 后端能拒越权，但前端把按钮给所有人看，用户点了才吃 403 | 权限矩阵、session、`<PermissionGate>`、`<AuthPanel>`、`/api/health` 暴露 `authMode` | 18 项新测试；studio-web 34 passed |
| 4 守卫 | 其余写路由全裸奔；且 `import_batches`/`content_jobs` 没有 project_id | 平台级权限点 + 7 条写路由挂守卫；**承认平台级而非伪造隔离** | 16 项新测试；api-server **89 passed** |
| 5 门控 | 前端只接了发布；且批量导入/创建任务的 UI 本就没渲染（死代码） | 三个真实写入口接上 `PermissionGate` | 3 项新测试；studio-web 37 passed |
| 6 权威 | 平台级角色仍靠前端自述的 `X-Content-Role` | 改为查 `project_members` 取最高角色；新增 `GET /api/auth/me/projects` | 5 项新测试；api-server 94 passed |
| 7 隔离 | **批次列表全表返回**，任何登录用户看到别人导入的商品（含成本价/FOB）；且可拿别人 batchId 建任务 | 批次加 `project_id`；任务经 `import_batch_id` 推导；统一 `data-scope` 判定 | 11 项新测试；api-server **105 passed** |

七处值得记住的设计取舍：

- **未知角色一律拒绝**（`role_code` 来自外部输入，放行等于把拼写错误变成提权漏洞）。
- **非成员返回 404 而非 403**（403 可用于枚举资源 id）。
- **401 与 403 分开处理**（403 绝不能清 token，否则用户莫名被登出、问题定位跑偏）。
- **宁可承认平台级，也不伪造项目隔离**：没有归属字段的表硬套项目级校验只能靠猜 id。
- **角色不信任前端声明**：伪造 `X-Content-Role: owner` 已被测试证明无法提权。
- **`project_id` 可空 = 未分配**，不伪造 id；**不设外键级联删除**（批次可能是唯一副本）。
- **任务不加冗余 `project_id`**，靠 `import_batch_id` join 推导，避免一致性维护成本。

**权限与数据隔离主线到这里闭环。** 继续往下需要先定两个业务口径（不是技术判断）：
批次能否跨项目、什么动作耗多少额度。
