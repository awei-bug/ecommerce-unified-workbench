8090 现在只做两件事：`/` 跳转到云购后台；`/legacy.html` 承载商品协作页。

### 3. 修复首屏会话问题（真根因）

前几轮反复出现的「首次打开报未检测到商家会话、必须手动刷新」，本轮定位到根因：

`PermissionGate.jsx` 的会话初始化里有这样一段——**只要本地有缓存 token 就直接标记 ready，不做校验**：

```js
const current = readToken();
if (current) { setToken(current); setReady(true); return; }   // ← 旧写法
```

服务重启后旧 token 已失效，页面拿它去请求必然 401，而换取新会话的分支因 `return` 从未执行。只有手动刷新（走 `hydrateSession` 内部校验）才恢复。

**修法**：删除短路分支，统一走 `hydrateSession`（它内部会先校验缓存 token，失效则用共享 Cookie 换新）。

## 三、明确未做到的部分

**这不是路由级合并。** 云购是 `vue-cli + JS`（20 view），跨境是 `Vite + TS + Pinia + vue-query`（17 view）——构建系统、状态管理、API 层都不同。把跨境页面真正搬进云购工程是数周工作量，本轮做的是：

- ✅ 一个入口（云购后台）
- ✅ 一套导航（云购侧栏）
- ✅ 一次登录（同域 Cookie）
- ❌ 一份前端源码（仍是 iframe 承载三个独立前端）

**用户视角的差异**：现在从导航看是一个系统，但内容区里仍是各模块自己的界面与次导航（例如跨境的二级侧栏、内容平台的顶部标签页）。视觉已统一（品牌色/底色/圆角/字体栈），但**布局结构未统一**。

## 四、为什么选择 iframe 承载而非源码迁移

1. **风险**：迁移 17 个 TS 组件到 vue-cli 需重写状态管理与 API 层，很容易破坏已通过的 217 + 11 项测试。
2. **收益**：用户能感知的是「一个入口 + 一次登录 + 一套导航」，这三项 iframe 已能达成。
3. **可逆**：将来真要迁移，`ModuleHostView` 换成真实组件即可，侧栏与路由不用动。
