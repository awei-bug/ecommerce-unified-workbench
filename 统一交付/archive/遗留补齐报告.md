### L3 · 服务端注销（已完成）

新增 `t_revoked_tokens` 表（`jti` 唯一索引、`tenant_id`、`staff_id`、`expires_at`）。

- `generate_token` 现在总是写入 `jti`
- `verify_token` 查到已吊销的 `jti` 即返回 `None`
- `POST /user/logout/` 记录 `jti` 并清 cookie

**实测**：
```
login: 200
me before logout: business status 200
logout: 200 {'msg': '已退出', 'revoked': True, 'status': 200}
me after logout: business status 401, msg: token 无效或已过期
session after logout: HTTP 401
PASS: 已吊销的 token 无法再使用
```

设计取舍：吊销表缺失时 `is_token_revoked` **fail-open**（返回未吊销），避免表未建就锁死所有人；`jti` 缺失的旧 token 无法吊销，故 `generate_token` 改为必设 `jti`。

## 三、过程中发现并修复的两个真实缺陷

### D-01 内容平台 `hydrateSession` 盲信旧 token

`hydrateSession` 只要有本地 token 就直接返回，不校验。重启服务后旧 token 失效（且现在支持吊销），页面永久卡在 401，必须清浏览器存储才能恢复。

**修复**：先验证（打 `/api/auth/me`），失败则 `clearSession()` 并换新；同时把 `apiBaseUrl` 从调用方传入，避免硬编码端口。新增 2 项测试覆盖。

### D-02 启动器强杀留孤儿

`Stop-Process` 杀 `start.py` 后子进程全部残留、内容 PG 集群也残留（`finally` 未执行）。

**修复**：子进程 PID 落盘 `.runtime/pids.json`，启动时 `reap_stale()` 先清理上次残留，再检查端口。
