## 二、界面观察：一个工作台，四个登录

这是最直观的问题。工作台左侧有 4 个模块，但**每个模块各有自己的登录**：

| 模块 | 登录方式 | 账号体系 | 截图 |
|---|---|---|---|
| 内容中心 | 顶部「登录」按钮 + 提示「需要云购商家登录后才可访问」 | 内容平台自有 | 06-content.png |
| 商城中心 | 独立登录页「登录后台」（团队标识/账号/密码） | 云购 | 02-shop.png |
| 跨境运营 | 独立登录页「登录运营中枢」 | 跨境固定演示 `demo/demo1234` | 07-cross-tab.png |

## 三、改进点清单（按优先级）

### P0 — 阻断「一次登录」体验，必须先修

**I-01 跨境前端登录页与后端已失效的演示登录不一致（本轮改动引入的回归）**

- 现象：`http://127.0.0.1:5175/` 登录页仍显示「演示账号 demo / demo1234」，点击「进入工作台」按钮转圈后无反应，停留在原页。
- 根因：`POST /api/v1/auth/login` 实测返回 **404**（本轮 T1 把演示登录在生产/默认模式下关闭了），但前端登录页未同步改造。
- 证据：`cross-api.log` 连续 `POST /api/v1/auth/login HTTP/1.1" 404`。
- 影响：**跨境模块当前完全无法通过 UI 进入**。
- 建议：前端登录页改为「云购账号登录」——调 5000 `/user/login/` 拿 token，存本地，后续请求带 `Authorization: Bearer`。或临时在工作台外壳统一登录后把 token 传给 iframe。

**I-02 「商品协作」页店铺列表加载失败（功能开关未开）**

- 现象：登录成功后显示「店铺列表暂不可用，请检查服务和功能配置」「店铺加载失败，请刷新」。
- 根因：`merchant_product_read_enabled` 默认 `False`（`app/core/config.py:64`），`GET /api/v1/merchant-products/shops/list` 实测 **404**。
- 补充：即便开关打开，还需 `merchant_shop_grants.can_read_products=1`（我已在预览库为 `shop-taobao-001` 置 1）。
- 建议：`start.py` 给 `cross_env` 注入 `MERCHANT_PRODUCT_READ_ENABLED=true`（仅本地演示），并在 README 标注该开关。

**I-03 内容平台前端未接统一会话**

- 现象：`http://127.0.0.1:5174/` 显示「设定库加载失败：需要云购商家登录后才可访问」。
- 现状：后端已改成 `authMode=strict`（无身份 401），但 React 前端仍走自己的登录态，没有向云购取 token。
- 建议：前端 `session.js` 增加「向工作台外壳请求云购 token」路径；或工作台外壳统一登录后通过 postMessage 下发 token。

### P1 — 影响观感与一致性

**I-04 四个模块视觉风格完全割裂**

- 云购后台：深绿主色（`#0f3a35` 类），Element Plus。
- 跨境：深蓝主色 + 大标题排版，Element Plus。
- 内容平台：浅紫渐变 + 圆角卡片，自定义 CSS。
- 工作台外壳：深墨绿侧栏。
- 建议：统一设计 token（主色、圆角、字号阶梯、间距），外壳与三模块共用一套；这是「看起来像一个系统」的关键。

**I-05 工作台外壳仍是 iframe 拼装**

- 现象：三个模块都是 `<iframe>` 嵌入，跨域导致外壳无法读取内部状态，也无法统一下发登录态。
- 证据：`document.querySelector('iframe#shop').contentDocument === null`（8080 与 8090 不同源）。
- 影响：I-01/I-03 的「统一下发 token」方案在 iframe 下需要 postMessage 配合，比同源方案复杂。
- 建议：按决策 D4，把跨境并入云购后台路由（同为 Vue3 + Element Plus，改造量可控），内容平台最后迁移。

**I-06 工作台顶部「服务端口已就绪」与真实状态可能不同步**

- 现象：跨境模块页顶显示「服务端口已就绪」，但实际登录接口 404。
- 根因：`/status` 只检测端口是否 listening，不代表接口可用。
- 建议：健康检查改为探测各服务的 `/health` 或 `/api/health` 返回内容，而非仅端口连通。

### P2 — 工程与运维

**I-07 跨境 `.env` 指向未运行的 PostgreSQL 5433**

- 现象：`跨境电商运营智能辅助系统/.env` 与 `backend/.env` 均为 `DATABASE_URL=postgresql+psycopg://ops_admin:...@127.0.0.1:5433/ops_command_center`，但 5433 无监听、Docker 未运行。
- 后果：直接启动跨境会 `ConnectionTimeout` 启动失败（我实测复现）。
- 本轮处置：通过 `UNIFIED_CROSS_DATABASE_URL` 指向已补迁移的 SQLite 副本绕过，未改 `.env`。
- 建议：二选一——启动 Docker 的 5433 实例；或把 `.env` 默认改为 SQLite，PG 配置移入 `.env.production`。

**I-08 跨境预览库停在 `20261015_0017`**

- 缺 `merchant_organization_mappings` / `merchant_shop_grants` / `merchant_access_audit` 三表，`products` 缺 `external_id` / `hub_product_id` 两列。
- 直接后果：带合法 token 访问跨境 → `500 no such table`。
- 建议：备份后执行 `alembic upgrade head`。我已在副本验证可行。

**I-09 强杀启动器不会级联清理子进程**

- 现象：`Stop-Process` 杀 `start.py` 后，5000/8080/3100/5174/5175/8110/8120 子进程残留，需手工逐个清理；内容 PG 集群也残留（`content_database.stop()` 在 `finally` 里未执行）。
- 建议：`start.py` 记录子进程 PID 到 `.runtime/pids.json`，启动时先清理上次残留。

**I-10 `shop-web`(8080) 曾静默退出**

- 本轮重启后正常，但此前多次出现编译成功后进程消失、无错误行。
- 建议：给 `shop-web` 增加存活检测与自动重启，或在日志中打印退出码。

## 四、建议的修复顺序

1. **I-02 + I-08**（配置与迁移，半小时级）→ 让「商品协作」页真正可用，这是当前唯一已接统一登录的页面。
2. **I-01**（跨境前端登录页改造）→ 解除跨境模块 UI 完全不可用的阻断。
3. **I-03**（内容前端接会话）→ 三个模块都能用云购账号进入。
4. **I-04 + I-05**（视觉统一 + 跨境并入宿主路由）→ 决策 D4 的主体工作。
5. **I-07 / I-09 / I-10**（运维健壮性）→ 可并行。

## 五、需要你确认的两点

1. **I-01 的修法**：跨境前端登录页是改成「云购账号登录」直接调 5000，还是等外壳统一登录后由 iframe postMessage 下发 token？前者独立可用、后者体验更统一但依赖 I-05。
2. **I-04 的视觉基准**：以云购后台（深绿 + Element Plus）为统一视觉基准，还是重新设计一套？这决定工作量。
